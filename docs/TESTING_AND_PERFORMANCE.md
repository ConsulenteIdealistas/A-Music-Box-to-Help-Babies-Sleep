## 1. テスト戦略

### 1.1 対象と層

テスト戦略の対象は、解析・音響・アプリの3対象とし、層は単体・統合・
実機の3層とする。各層の責務は、次のとおりとする（推奨）。

| 層 | 責務 |
|---|---|
| 単体 | 個々のスクリプト・関数・処理単位が、定められた入出力と規則に従うことを確認する。解析側の照合・統計の単位と、アプリ側の処理単位を含む |
| 統合 | 複数の単位を組み合わせた経路（抽出から統計まで、プリセットから音響出力まで、取得からキャッシュを経た再生まで）が、定められたとおりに結びつくことを確認する |
| 実機 | 実ブラウザ・実機でのみ現れる経路（再生中の経路、音圧、バックグラウンド継続、オフライン・低速回線の条件）を確認する。実機の確認は、机上の確認やスタブによる確認で代用しない |

自動化する範囲と手動で確認する範囲の区分は、【要決定：CONF-098】とする。区分を決める際は、実機音圧測定と聴感評価を手動の確認として
扱うかどうかを含めて決める。配置・命名・CI の実行範囲・網羅の方針は、
境界表のとおり MNT-007（CONF-099）の範囲とし、この文書では定めない。

### 1.3 デバイス・ブラウザの組合せ

実機テストの組合せは、対応環境の定義（MR-003、CONF-037）を前提とし、
次の軸で組合せ表を作る。組合せ表の具体的な行（採用する組合せ）は、【要決定：CONF-098】とする。

| 軸 | 組合せ表に含める区分 |
|---|---|
| OS とその版 | 対応環境の定義に挙げられた OS と版 |
| ブラウザとその版 | 対応環境の定義に挙げられたブラウザと版 |
| デバイスの機種クラス | 対応環境の定義に挙げられた機種クラス。端末スピーカー補正の端末クラス別プロファイル（`DESIGN.md` の「パラメータフロー」の節に記されたスマホ内蔵・小型外部・外部スピーカーの区分）との対応を含める |
| スピーカー形態 | 内蔵スピーカーと外部出力（外部スピーカー）の区分。最大音量リミッターの適用範囲（`DESIGN.md` の「最大音量リミッター」の項）との対応を含める |
| 音源の有無 | ループ音源が取得済みの場合と、未取得の場合の区分。ループ音源はリポジトリに含まれない（`app/assets/README.md` の冒頭の説明）ため、未取得の場合を組合せから落とさない |
| 回線条件 | オンライン・低速回線・機内モード（オフライン）の区分。完全オフライン動作（`DESIGN.md` の「アプリ機能・UX（PWA）」の節）の確認条件とする |

組合せ表の運用規則は、次のとおりとする。

- 組合せ表は、対応環境の定義が変わったときに見直す。見直しの契機と
責任者は、【要決定：CONF-098】とする。
- 実機テストの結果の記録には、組合せ表の行（OS・ブラウザ・版・
機種クラス・スピーカー形態・音源の有無・回線条件）を必ず記す。
組合せの記録がない結果は、実機テストの結果として扱わない。
- 対応環境の定義が未決定の間は、組合せ表の行を確定しない。未決定の
間に行った実機確認は、確認した組合せを記録したうえで、参考記録
として扱い、合否判定の根拠としない。

### 1.4 実機音圧測定の実施条件

実機音圧測定は、合否基準草案の A 層（実機 SPL）の定めと、
`DESIGN.md` の「最大音量リミッター」の項の定義を参照して行う。
測定条件の値そのものは、この文書では定めない。

測定手順の構造は、次のとおりとする。草案の候補は、草案の記載どおりに
候補として示し、決定としては扱わない。

| 項目 | 構造と参照 | 状態 |
|---|---|---|
| 測定距離 | 草案の測定手順の候補は 30 / 100 / 200 cm（hugh_2014 の手順に揃える）。合否判定の距離は、30 cm（最悪条件）か、実使用に近い 100 cm かを決める（草案の「決定事項（承認時に決める）」の節、第1項） | 【要決定：CONF-030】 |
| 指標とマイク条件 | 指標は LAeq,T・LAFmax・LCpeak。マイク位置は測定距離の点、向きは再生機に正対。乳児耳道補正の有無を記録する（草案の「A 層（実機 SPL）」の節） | 【要決定：CONF-030】 |
| 平均時間 T | 草案の候補は10分（T は再生1サイクル分を繰り返した10分間）。T の定義を決める（草案の「決定事項（承認時に決める）」の節、第4項） | 【要決定：CONF-030】 |
| 判定に使う端末音量 | 草案の再生条件は、実機（スマートフォン）の音量を段階ごとに固定し、各段階で測る。合否判定に使う音量段階は、最大か、想定する実使用段階かを決める（草案の「決定事項（承認時に決める）」の節、第3項） | 【要決定：CONF-030】 |
| 合格上限 | 候補と注意書きは、`DESIGN.md` の「最大音量リミッター」の項の決定事項表のとおりとする。候補はすべて借用値であり、家庭用アプリの基準として定められた値ではない旨の注意書きを含めて参照する | 【要決定：CONF-030】 |
| 不合格時の対応 | アプリ側の上限を下げるか、距離・音量の案内を出すか、両方を必須とするかを決める（草案の「決定事項（承認時に決める）」の節、第5項） | 【要決定：CONF-030】 |
| 測定器 | 合否判定は、校正済み機器での測定から始める。校正済み騒音計が無い段階では、測定値は相対比較にのみ使い、絶対値での合否判定はしない（草案の「A 層（実機 SPL）」の節）。校正済み騒音計が前提であること（IEC 61672）は、`analysis/phase4_preconditions_checklist_2026-11-17.md` の「前提条件」の節にも記されている | 規則として定義する。測定器の選定と校正の記録方法は 【要決定：CONF-098】 |
| 測定対象の組合せ | 測定を行うデバイス・ブラウザの組合せ、プリセット、楽曲、音量段階の範囲 | 【要決定：CONF-098】 |
| 測定環境 | 測定を行う場所の条件（暗騒音の扱いを含む）、測定の繰り返し回数、測定者の扱い | 【要決定：CONF-098】 |

測定の記録には、少なくとも次の項目を含める（推奨）。記録の様式は、【要決定：CONF-098】とする。

- 測定日、測定者、測定に用いた合否基準の登録状態と版
- 組合せ表の行（第1.3節）、プリセットと楽曲、端末音量の段階
- 測定距離、指標、平均時間 T、マイク位置と向き、乳児耳道補正の有無
- 測定器と校正の記録、測定環境の条件
- 測定値と、事前登録された基準に照らした合否の判定

上限値と測定条件が決定され、合否基準が事前登録されるまで、実機 SPL の
合否判定を行わない。この規則は、`DESIGN.md` の「最大音量リミッター」
の項の定めによる。

### 1.5 聴感評価の手順と判定基準

聴感評価は、`DESIGN.md` の「開発フェーズ」の節の Phase 4（音響評価）に
記された聴感評価の比較を、事前登録された手順と判定基準に沿って行う
ための枠組みとする。手順と判定基準の具体的な内容は、【要決定：CONF-098】とする。

聴感評価の手順は、少なくとも次の要素を含む構造とする（推奨）。

| 要素 | 決める内容 |
|---|---|
| 評価の目的 | 何を聴感で確認するのか（例：ループ境界の途切れの知覚、層間比の自然さ、遷移の滑らかさ）。目的ごとに評価を分けるか、一つの評価にまとめるかを含む |
| 評価者 | 評価者の人数、選定条件、聴力・経験の扱い、評価者への事前説明の範囲。評価者が設計値を知っているかどうか（盲検性の扱い）を含む |
| 試聴材料 | 評価に用いる音源（オフライン書き出しと実機再生のどちらか、または両方か）、プリセット、楽曲、提示順序、提示条件（音量・再生環境） |
| 評価手順 | 提示の回数、回答の方法、評価尺度の定義、休憩と順序効果の扱い |
| 判定基準 | 合格・不合格を分ける基準の構造（尺度値の集計方法、合格の条件）。基準の値は測定前に事前登録し、結果を見て動かさない |
| 記録 | 評価日、評価者、試聴材料と提示条件、回答の記録、集計結果、判定。試聴材料の版（音源とプリセットの版）を含める |

聴感評価の判定基準の値は、この文書では定めない。判定基準は、音響の
合否基準と同様に、測定前に事前登録する（第1.7節）。聴感評価の結果は、
実機音圧測定の合否判定の代用としない。音圧の合否は第1.4節の測定による。

### 1.6 回帰の範囲

変更時の回帰の範囲は、変更の種別ごとに確認範囲を定める表の構造とする。
表の具体的な行（変更の種別と確認範囲の対応）は、【要決定：CONF-098】とする。

回帰表の構造は、次のとおりとする（推奨）。

| 列 | 内容 |
|---|---|
| 変更の種別 | 変更の対象による区分（例：文献・統計パイプラインの変更、パラメータパッケージの変更、プリセットの変更、音源の変更、アプリの変更、キャッシュ・取得の変更）。区分そのものも要決定に含める |
| 確認範囲 | その変更の種別で実行する確認（単体・統合・実機の層、性能測定、実機音圧測定、聴感評価のうち、実行するもの） |
| 実施条件 | 回帰を実行する契機（例：公開前、版の変更時）。契機の定義を含む |
| 記録 | 回帰の実行結果の記録方法と、未実行の範囲がある場合の扱い |

回帰の規則は、次のとおりとする。

- パラメータパッケージの変更に伴う回帰は、`METHODOLOGY.md` の
「パラメータパッケージと受け渡し契約」の節の伝播と置き換えの定めと
整合させる。伝播の検証に失敗した版は、公開しない。
- 音源の再レンダーに伴う回帰には、デジタル音源の再現性の確認を含める。
再現性の基準として、合否基準草案の B 層（デジタル音源）の提案
（再レンダーの LUFS-I が登録値から ±0.5 LU 以内であること、dBTP が
0 dBTP 未満であること）を採用するかどうかは、【要決定：CONF-098】とする。草案は未登録であり、B 層の提案値は決定ではない。
C 層（音響モデル）については、草案自身が数値を置かないと記して
おり、実測データが揃った時点で測定前に別途登録するとしている。
C 層の許容差の扱いも、【要決定：CONF-098】とする。
- 回帰の範囲が未決定の間は、変更のたびに確認した範囲を記録し、
未確認の範囲があることを明示する。未確認の範囲がある版を、
確認済みとして扱わない。

### 1.7 合否基準の事前登録

音響の合否基準は、測定前に事前登録し、結果を見て動かさない。この規則は、
`analysis/pass_criteria_draft_2026-11-17.md` の冒頭の定めと、
`DESIGN.md` の「最大音量リミッター」の項の定めによる。

- 登録は、測定を始める前に人の承認をもって行う。承認されたら合否基準
文書を「登録済み」に改め、登録日と承認内容を冒頭に記録する
（草案の冒頭の定め）。
- 登録の内容は、草案の5つの決定事項（判定距離・合格上限・判定に使う
端末音量・平均時間 T・不合格時の対応）を含む。5つの決定事項の値は、【要決定：CONF-030】とする。
- 登録後に基準を変える場合は、変えた理由と承認を記録し、変える前の
測定結果に新しい基準を遡って適用しない。結果を見て基準を動かす
ことはしない。
- この文書は、草案を登録しない。草案は未登録のまま残す。

## 2. 性能目標の枠組みと測定手順

### 2.1 性能目標の項目と定義

性能目標は、次の項目について、定義・測定量・目標値を一つの表で定める。
目標値はすべて【要決定】とし、この文書では値を定めない。
測定手順は第2.5節、負荷条件は第2.3節に定める。

| 項目 | 定義（何を測るか） | 測定量の構造 | 目標値 |
|---|---|---|---|
| 応答時間 | 利用者の操作（BPM 調整、キー変更、ミキサー操作、プロファイル切替、プリセット適用）から、音響出力の変化が始まるまでの時間。操作の種別ごとに定義する | 操作の種別ごとの、操作時刻から音響変化の開始時刻までの時間 | 【要決定：CONF-042】 |
| 音声遅延 | 再生の開始操作から、音が出始めるまでの時間。応答時間とは別項目として定義する。遅延の定義（開始操作の時点と、音が出始めた時点の取り方）を含む | 再生開始操作の時刻から、音響出力の開始時刻までの時間 | 【要決定：CONF-042】 |
| 再生開始時間 | 曲の選択・変更から、その曲の音が出始めるまでの時間。デコードと再生時処理を含む、利用者が体感する開始までの時間とする | 曲の選択・変更の操作時刻から、音響出力の開始時刻までの時間 | 【要決定：CONF-042】 |
| ギャップレス・ループの許容途切れ | ループ境界での音の途切れの許容範囲。第2.2節の扱いによる | ループ境界での途切れの測定量（途切れの定義と測定方法を含む） | 【要決定：CONF-042】 |
| 同時処理の上限 | 同時に変更・実行できる操作と処理の範囲（例：複数のパラメータの同時変更、遷移中の操作）。上限の定義（同時変更の数、重なりの条件）を含む | 同時変更の条件と、その条件下での応答時間・途切れの測定量 | 【要決定：CONF-042】 |
| メモリ使用量の上限 | 再生中のメモリ使用量の上限。デコード済み音源の保持量を含む。詳細な保持・解放条件は第2.6節に定める | 再生中のメモリ使用量。測定条件は第2.3節による | 【要決定：CONF-042】 |
| CPU 使用量の上限 | 再生中・操作中の CPU 使用量の上限。測定条件（端末条件・負荷条件）を含む | 再生中・操作中の CPU 使用量 | 【要決定：CONF-042】 |
| 電池消耗と発熱 | 長時間連続再生における電池消耗と発熱の許容範囲。測定条件と許容範囲は第3.3節に定める | 電池残量の変化と、端末の温度の測定量 | 【要決定：CONF-043】（CONF-042 との対応は第3.3節に記す） |

目標値の決定に当たっては、操作の種別・端末条件・負荷条件ごとに
目標値を分けるかどうかを含めて決める。一つの値ですべての条件を
代表させる場合は、その旨と理由を決定の記録に残す。

### 2.2 「完全シームレス」の測定可能な扱い

`DESIGN.md` の「3層レイヤーの音響処理」の節は、リバーブテイル
折り返し処理（2周分書き出しから後半を切り出し）による「完全シームレス」
なループを求めている。「完全シームレス」は検証不能な絶対表現であるため、
合否判定には次の扱いを適用する。

- ループの合否判定は、「完全シームレス」という表現そのものではなく、
第2.1節の「ギャップレス・ループの許容途切れ」の許容値に照らして行う。
許容値は、【要決定：CONF-042】とする。
- 許容値が未決定の間は、ループの合否判定を行わない。ループ境界の
途切れを測定した場合は、測定量と測定条件を記録し、合否の判定は
行わない。
- `DESIGN.md` の原文の表現をこの文書で書き換えない。原文の表現を
測定可能な許容値の表現に置き換えるかどうかは、【要決定：CONF-042】とする。置き換えを行う場合は、置き換え後の表現と許容値をあわせて
決定し、置き換えの記録を残す。
- ループ化の手順（`app/assets/README.md` の「生成手順」の節に記された、
最後の可聴サンプル（−60 dB 閾値）まで＋無音 1.0 秒を残し、ゼロ交差で
切る手順）と、再生時の途切れ許容値との対応は、【要決定：CONF-042】とする。生成手順の定めと許容値の定めが、互いに矛盾しないことを
確認する。

### 2.3 負荷条件

性能測定の負荷条件は、次の軸で定める。負荷条件の具体的な値と組合せは、【要決定：CONF-042】とする。

| 軸 | 内容 |
|---|---|
| 端末条件 | 確認対象とする端末条件（機種クラス、性能の区分）。低性能端末を対象に含めるかどうかと、低性能端末の定義を含む。端末条件の区分は、第1.3節の組合せ表と整合させる |
| 同時操作の条件 | 同時に変更するパラメータの組合せと数、遷移中の操作の有無、連続操作の間隔の扱い |
| 再生条件 | 再生中の層の組合せ（3層のうち再生する層）、プリセット、楽曲、音量段階 |
| バックグラウンド条件 | 画面消灯・タブ非表示の有無。第3章の条件区分と整合させる |
| 回線・取得条件 | 音源の取得状態（取得済み・未取得）、回線条件（オンライン・低速回線・オフライン）。初回取得とキャッシュのコスト測定（第4章）との対応を含む |
| 継続時間の条件 | 測定を行う再生の継続時間。長時間再生の測定（第3.3節）との対応を含む |

負荷条件の記録には、測定に用いた条件の組合せをすべて記す。条件の記録が
ない測定結果は、性能目標に照らした合否判定の根拠としない。

### 2.4 測定の共通規則

性能測定に共通する規則は、次のとおりとする。

- 測定手順と測定条件は、測定の前に定める。測定の結果を見て、手順・
条件・目標値を動かさない。
- 目標値が未決定の項目については、測定を行った場合でも合否判定を
行わない。測定量と測定条件を記録し、目標値の決定後に判定できる
形で残す。
- 測定結果の記録には、測定日、測定に用いた版（アプリ・音源・
プリセットの版）、組合せ表の行（第1.3節）、負荷条件（第2.3節）、
測定量、測定手順への参照を含める。版の記録方法は、版管理の決定と整合させる。
- 測定に用いた器具・手段（実機の計測機能、ブラウザの計測機能、外部の
測定器具の別）と、その精度・限界を記録する。器具・手段の選定は、【要決定：CONF-042】とする。
- 同じ条件での測定の繰り返し回数と、測定量の集計方法（代表値の取り方）
は、【要決定：CONF-042】とする。

### 2.5 測定手順

次の表は、測定対象ごとの測定手順の構造を定める。手順の詳細と判定に
用いる目標値は、【要決定：CONF-042】とする。電池消耗と発熱の測定手順は
第3.3節、バックグラウンド継続の測定手順は第3.4節に定める。

| 測定対象 | 手順の構造（何を、どの順序で測るか） | 記録項目 |

| ループの途切れ | ループ境界を含む再生を行い、境界付近の音響出力を記録する。記録した出力から、途切れの測定量を求める。測定に用いる楽曲・ループ音源・再生条件を事前に定める | 楽曲・音源の版、再生条件、境界付近の記録、途切れの測定量 |
| 応答時間 | 操作を行い、操作時刻と音響変化の開始時刻を記録する。操作の種別ごとに測定する。同時変更の条件での測定を含む | 操作の種別、操作時刻、音響変化の開始時刻、応答時間、負荷条件 |
| 音声遅延と再生開始時間 | 再生の開始操作・曲の変更操作を行い、操作時刻と音響出力の開始時刻を記録する。デコードを含む場合と、デコード済みの場合を区別して記録する | 操作の種別、操作時刻、音響出力の開始時刻、デコードの有無、音源の取得状態 |
| 同時処理 | 同時変更の条件を設定し、その条件下での応答時間・途切れ・音切れの有無を測定する。負荷時の劣化挙動（音切れ・遅延の現れ方）を記録する | 同時変更の条件、応答時間、途切れの測定量、音切れの有無、劣化挙動の記録 |

残作業とする。測定の実施は、目標値と手順の詳細の決定の後に行う。

### 2.6 メモリ使用量の上限と保持・解放の条件

メモリ使用量の上限、デコード済み音源の保持・解放の条件、メモリ逼迫時
の挙動を定める。ループ音源は4件で合計約 14 MB のファイル容量であり
（`app/assets/README.md` の「対応表（2026-11-15 生成）」の節）、
ファイル容量とデコード後の保持量は別物である。デコード後の保持量の
上限は、この節の決定による。上限と条件の値は、この節の各項目の決定に
よる。

| 対象 | 保持・解放の条件の構造 |
|---|---|
| デコード済みループ音源 | 保持する音源の範囲（再生中の曲・複数曲の保持の別）、保持の開始と終了の契機、解放・破棄の契機 |
| 3層の音響グラフ | 音響グラフの構成要素の保持の範囲、プリセット切替時と曲変更時の扱い |
| リバーブ | リバーブの処理に伴う保持の範囲と、解放の契機 |
| ノイズ生成 | ノイズ生成の処理に伴う保持の範囲と、解放の契機 |

- メモリ使用量の上限：上限を対象ごとに定めるか、合計で定めるか、
両方で定めるかを含めて定めること。上限の値と定め方は、
【要決定：CONF-042】とする。
- 保持の条件：デコード済み音源を保持する条件（再生中の保持、複数曲の
保持の別と範囲を含む）を定めること。保持の条件は、
【要決定：CONF-042】とする。
- 解放・破棄の条件：デコード済み音源と音響グラフの構成要素を解放・
破棄する条件（プリセット切替時・曲変更時・再生停止時の扱いを含む）を
定めること。解放・破棄の条件は、【要決定：CONF-042】とする。
- 低メモリ端末での条件：低メモリ端末を対象に含める場合の条件
（低メモリ端末の定義と、その条件下での保持・解放の扱いを含む）を
定めること。低メモリ端末での条件は、【要決定：CONF-042】とする。
端末条件の区分は、第2.3節の負荷条件と整合させる。
- メモリ逼迫時の挙動：メモリが逼迫した場合の挙動（停止・劣化・通知の
別と、利用者への通知の有無と内容を含む）を定めること。逼迫時の挙動は、
【要決定：CONF-042】とする。表示の内容は、障害処理の定義

- 測定：メモリ使用量の測定は、第2.4節の共通規則と第2.5節の測定手順に
よる。測定の記録には、保持しているデコード済み音源の数と、測定の区間
（再生開始直後・継続中・操作中・プリセット切替時）を含めること（推奨）。

## 3. バックグラウンド再生の継続条件と長時間再生

`DESIGN.md` の「アプリ機能・UX（PWA）」の節はバックグラウンド再生を
求め、`DESIGN.md` の「プロファイル」の節は深い睡眠維持（心音とさざ波
のみの極小音量での継続）を定める。スリープタイマーは 15〜30 分と
される。この章は、継続条件・駆動方法・長時間再生の測定条件と
許容範囲の枠組みを定める。具体的な条件と値は、【要決定：CONF-043】とする。

### 3.1 継続条件の区分

バックグラウンド再生の継続条件は、次の区分ごとに定める。各区分での
再生の継続・抑制・中断・復帰の扱いは、【要決定：CONF-043】とする。
復帰時の音量・BPM の扱いは、状態遷移の定義（MR-005、CONF-038）と
整合させる。

| 区分 | 定める内容 |
|---|---|
| 画面消灯 | 画面が消灯した条件下での再生継続の条件。消灯後の継続時間の扱いを含む |
| タブ非表示 | タブが非表示になった条件下での再生継続の条件。ブラウザによる抑制の扱いを含む |
| 割り込み | 着信・通知・他アプリによる割り込み時の再生の扱い（継続・一時停止・中断）と、割り込みの種別ごとの扱い |
| 復帰 | 抑制・中断からの復帰の条件と契機。復帰時の再生状態（再生位置・音量・BPM・減速カーブの進行位置）の扱いを含む |
| タイマー後の継続 | スリープタイマー（15〜30 分）の終了後の継続の扱い。タイマー終了時に再生を止めるか、継続するかを、プロファイル（深い睡眠維持を含む）との対応で定める |
| 長時間の継続 | タイマーの範囲を超える長時間の連続再生における継続条件。電池・発熱の条件（第3.3節）との対応を含む |

継続条件の決定に当たっては、対応環境の定義（MR-003、CONF-037）に
挙げられた OS・ブラウザ・版ごとに、条件が異なるかどうかを含めて決める。
条件が環境ごとに異なる場合は、環境ごとの条件を組合せ表（第1.3節）と
対応づけて記録する。

### 3.2 減速カーブの駆動方法と中断時の扱い

減速カーブ（エントレインメントの減速）とイージングを、どの時計・
駆動方法で進めるかは、【要決定：CONF-043】とする。決定する内容は、
次のとおりとする。

- 減速カーブとイージングの進行を駆動する方法（何を時間の基準とし、
どのような周期・契機で更新するか）。
- バックグラウンド下（画面消灯・タブ非表示）で、減速カーブの進行が
止まるか、進むか、遅れるか。
- 抑制・中断が起きた場合の、減速カーブの進行位置の扱い（中断した
位置から再開するか、中断中の経過時間を反映するか、最初から
やり直すか）。
- 復帰時に、減速カーブの進行位置と音量・BPM が整合することを
確認する方法。

実装物の現状として、`app/app.js` には、トゥイーンの更新を一定間隔で
行う処理（`setInterval` による 50 ミリ秒間隔の更新）と、心音の
スケジュールを `setTimeout` で行う処理が確認できる。また、画面の
表示状態やバックグラウンド継続に関する処理（`visibilitychange`・
`MediaSession`・`wakeLock` に相当する記述）は、`app/app.js`・
`app/index.html`・`app/sw.js` の読み取りでは確認できなかった。
これらは実装物の現状の記録であり、仕様の決定ではない。駆動方法の
決定は、上記の【要決定】による。

### 3.3 長時間再生の電池・発熱

長時間の連続再生における電池消耗と発熱について、測定条件と許容範囲を
定める。測定条件の構造はこの節に定め、許容範囲の値は、【要決定：CONF-043】とする。性能目標の枠組み（第2.1節）では、電池消耗
と発熱の行を CONF-043 に割り当てており、CONF-042 の性能目標の決定と
あわせて確認する。

測定条件の構造は、次のとおりとする（推奨）。

| 項目 | 内容 |
|---|---|
| 測定対象の条件 | 測定を行うデバイス・ブラウザの組合せ（第1.3節）、再生条件（層の組合せ・プリセット・楽曲・音量段階）、バックグラウンド条件（画面消灯・タブ非表示の有無） |
| 測定時間 | 測定を行う再生の継続時間。スリープタイマーの範囲（15〜30 分）と、それを超える長時間の区分を含む。継続時間の値は 【要決定：CONF-043】 |
| 測定量 | 電池残量の変化、端末の温度の測定量。測定量の定義と測定手段を含む |
| 測定の区間 | 測定を開始・終了する時点と、区間内での測定の間隔 |
| 許容範囲 | 電池消耗と発熱の許容範囲の値。測定条件ごとに許容範囲を分けるかどうかを含む |

測定の記録には、測定対象の条件、測定時間、測定量の推移、測定手段、
測定時の端末の状態（充電の有無を含む）を含める。低電力状態での挙動
（端末の省電力の条件下での再生の扱い）は、【要決定：CONF-043】とする。

### 3.4 検証手順

バックグラウンド継続の検証は、実機での確認手順として、次の構造で
行う。手順の詳細は、【要決定：CONF-043】とする。

- 検証は、第1.3節の組合せ表に挙げられた組合せのうち、継続条件の
決定で対象とした組合せで行う。対象とする組合せは、継続条件の
決定に含める。
- 検証の条件は、第3.1節の区分（画面消灯・タブ非表示・割り込み・

## 4. 初回取得とキャッシュのコスト

`DESIGN.md` の「アプリ機能・UX（PWA）」の節は、完全オフライン動作
（ローカルキャッシュ、機内モード可）を求める。この章は、初回取得と
キャッシュのコストモデルと予算の構造を定める。キャッシュ戦略・
版管理・強制更新経路の機構は、境界表のとおりこの文書の範囲外とする。

### 4.1 コストモデル

コストは、次の項目に分けて算定・測定する。各項目の算定方法は
第4.3節に定める。

| コスト項目 | 内容と証拠 |
|---|---|
| 初回取得量 | 初回利用時に取得する内容物の量。内容物の一覧と取得元は、【要決定：CONF-044】とする。ループ音源は4件で合計約 14 MB、形式は 44.1 kHz / 16 bit / モノラル、長さは 22.1〜49.2 秒であり、リポジトリには含まれない（`app/assets/README.md` の「対応表（2026-11-15 生成）」の節）。アプリのシェル（`app/index.html`・`app/style.css`・`app/app.js`・`app/manifest.webmanifest`・`app/presets.json`）の取得量は、取得時点の実測による |
| 更新時の再取得量 | 音源・シェル・プリセットの更新時に、再取得する範囲の量。再取得の範囲の規則は、【要決定：CONF-044】とする。全量を再取得するか、差分のみを再取得するかの規則を含む |
| 蓄積容量 | 端末に蓄積されるキャッシュの容量。キャッシュ対象と容量上限は、【要決定：CONF-044】とする。蓄積容量の算定には、ループ音源の合計量と、シェル・プリセットの量を含める |
| 通信量 | 初回取得と更新時の通信量の合計。通信量の上限は、【要決定：CONF-044】とする。低速回線時の挙動の定義（MR-004、CONF-039）と整合させる |

コストモデルの算定に当たっては、取得に失敗・中断した場合の再取得の
扱いを含める。取得失敗・中断時の挙動と表示の定義は、MR-004
（CONF-039）の範囲とし、この文書ではコストへの影響の算定方法のみを
定める。

### 4.2 予算

次の予算は、すべて【要決定】とし、この文書では値を定めない。
予算の決定に当たっては、予算を超えた場合の扱い（取得の中止・警告・
継続の別）を含めて決める。予算超過時の挙動と表示の定義は、MR-004
（CONF-039）と整合させる。

| 予算項目 | 内容 |
|---|---|
| 初回取得量の予算 | 初回利用時の取得量の上限 |
| 更新時の再取得量の予算 | 一回の更新時の再取得量の上限 |
| 蓄積容量の予算（容量上限） | 端末に蓄積されるキャッシュの容量の上限。容量超過時の挙動（破棄・警告・継続の別）を含む |
| 通信量の予算 | 初回取得と更新時を合わせた通信量の上限。期間の区切りがある場合は、その区切りを含めて決める |

### 4.3 算定と測定の手順

コストの算定と測定の手順は、次のとおりとする。手順の詳細は、【要決定：CONF-044】とする。

- 初回取得量と蓄積容量は、取得する内容物の一覧と、各内容物の量から
算定する。内容物の一覧は、取得元の定義（CONF-044）と対応づける。
算定の結果は、取得時点の実測と照合する。
- 更新時の再取得量は、更新の前後で再取得の対象となった内容物の量から
算定する。再取得の範囲の規則（CONF-044）と対応づけて記録する。
- 通信量は、取得と更新の通信の実測による。測定に用いる手段と、
測定の条件（回線条件・取得状態）は、事前に定める。
- 算定と測定の記録には、内容物の一覧、取得元、各内容物の量、算定結果、
実測結果、予算に照らした判定を含める。予算が未決定の間は、合否判定を
行わず、算定結果と実測結果の記録に留める。
- 容量逼迫時の扱い（端末の容量が逼迫した場合の、キャッシュの破棄・
維持の扱い）は、コストへの影響の観点から、【要決定：CONF-044】とする。破棄の機構そのものは、キャッシュ戦略の範囲（SEC-006・
ARC-012、CONF-044）とする。

実装物の現状として、`app/sw.js` には、アプリのシェル用のキャッシュと
音源用のキャッシュを分け、音源を任意キャッシュ（失敗許容）として扱う
構造が確認できる。これは実装物の現状の記録であり、仕様の決定ではない。
キャッシュの対象・版管理・更新確認の規則は、境界表の範囲とする。

### 4.4 境界

この章の範囲と、隣接する決定の範囲の境界は、次のとおりとする。

- コストモデル・予算の構造・算定と測定の手順は、この章が定める。
- キャッシュ戦略（更新確認の時期・方法、古い内容の扱い）、版管理、
無効化条件、容量規則の機構、安全上の修正のための強制更新の経路と
更新の完了確認、端末上の版の確認方法は、SEC-006・ARC-012
（CONF-044）の範囲とし、この章では定めない。機構の定義は、
`DESIGN.md` の「アプリ機能・UX（PWA）」の節の「キャッシュ戦略」の項と、

## 5. ループとデコードのコスト分析

`DESIGN.md` の「3層レイヤーの音響処理」の節は、リバーブテイル
折り返し処理によるループを求め、`DESIGN.md` の「技術選定」の節は
再生・ギャップレスループの役割に `Howler.js` を挙げる。この章は、
ループとデコード・再生開始のコストについて、分析と測定で明らかに
すべき事項を定める。許容値と時間予算の値は、【要決定：CONF-042】とする。

### 5.1 分析対象

分析の対象は、次のとおりとする。

| 対象 | 内容 |
|---|---|
| デコード | ループ音源のデコードに要する時間と、その条件（音源の長さ・形式・端末条件）による変化。ループ音源は最長 49.2 秒、合計約 14 MBである（`app/assets/README.md` の「対応表（2026-11-15 生成）」の節） |
| 再生時処理 | 再生時に行われる処理（統合伝達曲線の適用と RMS 正規化）に要する時間。統合伝達曲線の適用と RMS 正規化が再生時に行われることは、`app/assets/README.md` の「対応表（2026-11-15 生成）」の節の末尾に記されている |
| ループ境界 | ループ境界での途切れの測定量と、その条件による変化。第2.2節の許容値との対応を含む |
| 再生開始 | 曲の選択・変更から音が出始めるまでの時間の内訳（取得・デコード・再生時処理・再生開始の各段階）。段階ごとの時間の分離を含む |
| 律速条件 | デコードと再生時処理のどちらが律速になるかの条件。端末条件による変化を含む |
| 端末条件 | 低性能端末を含む、確認対象とする端末条件。端末条件の区分は、第2.3節の負荷条件と整合させる |

実装物の現状として、`app/app.js` には、音源の取得（`fetch`）と
デコード（`decodeAudioData`）を行い、再生する音源にループを設定する
処理が確認できる。これは実装物の現状の記録であり、仕様の決定ではない。
音響グラフの構成（`Web Audio API` 単体か、技術選定の節に挙げられた
ライブラリを併用するか）は、第6.1節の分析対象に含める。

### 5.2 分析と測定の方法

分析と測定の方法は、次のとおりとする。方法の詳細は、【要決定：CONF-042】とする。

- デコードに要する時間と、再生時処理に要する時間を、分離して測定する。
分離できない場合は、分離できない理由と、合計時間の測定方法を記録する。
- 測定は、確認対象とする端末条件のそれぞれで行う。端末条件ごとの
測定結果を比較し、律速条件の違いを記録する。
- 再生開始時間は、段階ごとの内訳（取得・デコード・再生時処理・
再生開始）を記録する。取得を含む場合と、取得済みの場合を区別する。
- ループ境界の途切れは、第2.5節の測定手順による。ループ化の手順
（第2.2節）と、測定結果との対応を記録する。
- 分析の結果は、測定条件（端末条件・音源・再生条件）とあわせて記録し、
時間予算の決定の根拠とする。分析の実施（測定の実行）は、この文書の
範囲外の残作業とする。

### 5.3 受入の構造

受入は、次の構造で行う。許容値と時間予算の値は、【要決定：CONF-042】とする。

- ループ途切れの許容値（第2.1節）に照らした、ループ境界の測定結果の
合否判定。
- デコードと再生時処理の時間予算に照らした、測定結果の合否判定。
時間予算は、デコードと再生時処理を分けた予算とするか、合計の予算と
するかを、決定に含める。
- 再生開始時間の上限（第2.1節）に照らした、測定結果の合否判定。
- 許容値・時間予算・上限が未決定の間は、合否判定を行わず、測定結果の
記録に留める。

## 6. リアルタイム操作の応答分析

`DESIGN.md` の「システム構成」の節は、状態定義・イージングエンジン・
パラメータ連動制御・音響レンダリングの4要素を定め、`DESIGN.md` の
「イージング関数の使い分け」の節はパラメータごとに異なる曲線を適用する
ことを求める。この章は、リアルタイム操作の応答と、イージング・連動
計算のコストについて、分析と測定で明らかにすべき事項を定める。
上限と周期の値は、【要決定：CONF-042】とする。

### 6.1 分析対象

分析の対象は、次のとおりとする。

| 対象 | 内容 |
|---|---|
| パラメータ更新の周期と駆動方法 | パラメータの更新を行う周期と、更新を駆動する方法。更新の周期が、応答時間と音響の滑らかさに与える影響を含む |
| 1更新あたりの計算量 | 1回の更新で行われる計算の内容と量。パラメータ連動制御（Gain / Filter / Reverb / Modulation）の各要素の計算を含む |
| 同時変更時の負荷 | 複数のパラメータを同時に変更した場合の負荷と、応答時間・途切れへの影響。同時変更の条件は、第2.3節の負荷条件による |
| 負荷時の劣化挙動 | 負荷が高い条件下での挙動（応答の遅延・音切れ・遷移の乱れの現れ方）。劣化挙動の定義は、状態遷移の定義（MR-005、CONF-038）と整合させる |
| 音響グラフの構成 | 音響グラフの構成（`Web Audio API` 単体か、`DESIGN.md` の「技術選定」の節に挙げられたライブラリを併用するか）と、併用時のコスト。構成の決定は、【要決定：CONF-042】とし、ライブラリの採用条件の決定（TECH-004 の範囲）と整合させる |
| クロスフェード差し替え | ローパス変更時に、同じ再生位置から新しいフィルタ版へクロスフェードして差し替える処理（`DESIGN.md` の「プリセットの JSON 形式」の節）のコストと、差し替え時の途切れの扱い |
| BPM 同期の変調 | さざ波の振幅変調を心音の BPM に同期させる処理（`DESIGN.md` の「さざ波」の定義の節）のコストと、BPM 変更時の追従の扱い |

実装物の現状として、`app/app.js` には、トゥイーンの更新を一定間隔で
行う処理（`setInterval` による 50 ミリ秒間隔の更新）が確認できる。
これは実装物の現状の記録であり、仕様の決定ではない。更新の周期と
駆動方法の決定は、上記の【要決定】による。

### 6.2 分析と測定の方法

分析と測定の方法は、次のとおりとする。方法の詳細は、【要決定：CONF-042】とする。

- パラメータ更新の周期と駆動方法を、分析の前提として記録する。
周期と駆動方法が未決定の場合は、分析に用いた前提を記録し、
前提が変わった場合に分析をやり直す条件を定める。
- 応答時間は、第2.5節の測定手順により、操作の種別ごとに測定する。
同時変更の条件での測定を含む。
- 同時変更時の負荷は、同時変更の条件を変えて測定し、負荷と応答時間・
途切れの関係を記録する。
- 音響グラフの構成ごとに、コストの測定結果を分けて記録する。構成が
未決定の場合は、測定に用いた構成を記録する。
- 分析の結果は、測定条件（端末条件・負荷条件・音響グラフの構成）と
あわせて記録し、操作応答時間の上限の決定の根拠とする。分析の実施
（測定の実行）は、この文書の範囲外の残作業とする。

### 6.3 受入の構造

受入は、次の構造で行う。上限の値は、【要決定：CONF-042】とする。

- 操作応答時間の上限（第2.1節）に照らした、測定結果の合否判定。
操作の種別ごとに判定する。
- 同時変更時の負荷条件の下での、応答時間と途切れの測定結果の合否判定。
- 負荷時の劣化挙動について、定められた挙動（MR-005、CONF-038 の範囲）
との整合の確認。
- 上限が未決定の間は、合否判定を行わず、測定結果の記録に留める。
